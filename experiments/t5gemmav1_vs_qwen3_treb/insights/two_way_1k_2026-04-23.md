# TReB 1000-sample rerun: T5Gemma v1 2B-2B UL2-IT vs Gemma-2-2B-IT

*2026-04-23 · same-lineage architecture comparison · DeepSeek-v3.2 judge*

## TL;DR

On **1000 stratified TReB English samples**, T5Gemma v1 (encoder-decoder, 5.6B)
beats its same-lineage decoder-only counterpart Gemma-2-2B-IT (2.6B) on
overall correctness (**35.6 % vs 30.7 %**), mean judge score
(**4.47 vs 4.02**), and 16 of 26 tasks. The encoder-decoder's advantage is
concentrated in **retrieval and fact-checking** (+12 pp and +11 pp) —
consistent with the earlier 250-sample result, now with 4× the statistical
power and a reproducible, API-based judge.

Encoder-decoder costs **2× the parameters** for **+5 pp CORRECT**, and
Gemma-2 still wins **Understanding by +15 pp**, so the architecture choice
is a task-mix question rather than a blanket win. Both models are wrong on
**55 %** of samples — the 2–5B ceiling from the 3-way writeup reproduces.

## Setup

| Item | Value |
|---|---|
| Dataset | TReB English, phase-0 filtered to ≤ 4K tokens, stratified down to 1000 (seed=42, `sample_1000.py`) |
| Model A | `google/t5gemma-2b-2b-ul2-it` — Google-IT'd encoder-decoder, 5.6B total, 2026 T5Gemma v1 |
| Model B | `google/gemma-2-2b-it` — same pretraining base as Model A, decoder-only, 2.6B, 2024 |
| Mode | TCoT (text chain-of-thought, `{"answer": X}` JSON on last line) |
| Generation | greedy · `max_new_tokens=256` · `apply_chat_template=True` · `eos_token_id=[1, 107]` |
| Backend | HF transformers (`hf_seq2seq` for T5Gemma, `hf_causal` for Gemma-2) |
| Judge | DeepSeek v3.2 (`deepseek/deepseek-v3.2` via OpenRouter, 12-mode taxonomy, 0–10 score) |
| Hardware | 1× H100 80 GB HBM3, EU-NL-1 |
| Wall-clock | T5Gemma ~ 80 min @ bs=1 · Gemma-2 ~ 15 min @ bs=4 · judge ~ 18 min @ 12 workers |

Both models share the same Gemma-2 pretraining base and the same
Google-published SFT + RLHF recipe; **architecture is the only dimension
that moves** between them (T5Gemma v1 is described in its tech report as
"an encoder-decoder adapted from Gemma-2-2B-IT via UL2 + SFT"). That's what
makes this comparison clean.

**Two modes track architecture:**

1. **Gemma-2 refuses ~4× more** (3.7 % vs 1.0 %) — same signal as the
   250-sample run. Both checkpoints come out of the same SFT pipeline,
   so this is almost certainly a **decoder-only vs encoder-decoder
   calibration difference** rather than data/prompting.
2. **T5Gemma TRUNCATED fell to 1.9 %** (from 17.7 % in the 250-run). The
   250-sample set over-indexed on Table_Summary / retrieval (long TCoT
   outputs); the 1000-sample stratified set doesn't. 256 tokens is
   enough in aggregate — T5Gemma is *not* a structurally long generator
   at TReB.

**WRONG_SELECTION is the dominant failure for both** (~36–39 %). Both
models read the table and pick the wrong row/column/cell. This is a
capability gap both have at this scale, not an architecture story.

**Reads:**

- **Retrieval + fact-checking (n = 396, ~40 % of the benchmark) is
  T5Gemma's strongest advantage.** Mechanistically consistent with
  cross-attention — the decoder can re-attend to the encoded table at
  every generation step, which is exactly the shape of "find this
  specific thing" and "does this claim entail from the table" problems.

- **Understanding (n = 84) — Gemma-2 wins +15 pp.** These tasks
  (Understanding, Instruction_Following) reward generic instruction-
  following / concise rephrasing rather than table lookup. Most are
  reference-free (judged by constraint satisfaction against the
  question), where decoder-only SFT calibration does better.

- **Analysis (n = 104) — both at 2.9 %**. Hypothesis testing, outlier
  detection, and distribution testing require numeric reasoning neither
  2–5B model handles at the benchmark's level. Raises the 2–5B ceiling
  flag from the 3-way writeup; it reproduces here.

- **Computation (n = 223) — both wrong on 60 %.** Math and code
  generation are hard for both; T5G's +3.6 pp is mostly driven by
  Mathematical_Reasoning being where G2 *wins* (+1.27 mean) but *doesn't
  hit CORRECT more often* — it gets partial credit. Check per-task
  deltas below.

## Take-aways

1. **Encoder-decoder helps retrieval + fact-checking at 2–5B scale.** The
   signal from the 250-run is real; at 4× the data it holds. +12 pp on
   retrieval, +11 pp on fact-checking. Cross-attention is a real
   architectural lever for table lookup.

2. **It's not free — 2× params for +5 pp overall.** If your task mix is
   heavily lookup / entailment / cell-selection, T5Gemma pays for itself.
   For open-ended understanding or math CoT, pick Gemma-2.

3. **2–5B ceiling is load-bearing.** 55 % of samples wrong for both;
   analysis category is floored at ~3 %; multi-step at ~10 %. Either
   scale past 4B or design your benchmark expectations around this.

4. **Gemma-2 REFUSAL quirk is not noise.** 3.7 % vs 1.0 % reproduces the
   250-run finding at larger n. Both models come out of the same
   Google SFT pipeline, so the gap is either decoder-only-specific
   calibration or a T5Gemma SFT re-cal during UL2 adaptation — worth
   chasing if you care about refusal-sensitive deployments.

5. **The 250-run TRUNCATED number (17.7 %) was a sampling artifact**,
   not a T5Gemma problem. Stratified 1000-sample TRUNCATED rate is
   1.9 %. No reason to raise `max_new_tokens` above 256 for T5Gemma v1.
